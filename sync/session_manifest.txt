## VBA-side bug analysis (operator-caught, 2026-09-19/20): missing On Error handlers

  While reviewing the JS-side fix above, operator asked directly:
  "since the auto-run-on-open call has no error handling" -- is that
  VBA or JS? Confirmed JS-only (taskpane.ts's lockHyperlinks/
  Office.onReady). But the operator's follow-up question ("if VBA, I
  have standard error handling -- confirm") prompted checking the VBA
  side too, and found a REAL, separate gap:

  - `ThisDocument.Document_BeforeSave` (added this session, b95bd60)
    has **no `On Error GoTo PROC_ERR` at all** -- unlike
    `CheckForConflictingRibbonAddIn`, a few lines below it in the SAME
    file, which has the full PROC_ERR/Debug.Print pattern. Confirmed by
    reading the current file directly.
  - `basTEST_aeBibleTools.LockBookHyperlinks` (also touched this
    session, gained the `silent` parameter) has only a NARROW
    `On Error Resume Next` / `On Error GoTo 0` bracket around the
    style-existence check -- no top-level `On Error GoTo PROC_ERR` for
    the rest of the Sub (the three Find/Hyperlinks loops, the
    `ColorFromName` call). Confirmed by grepping every `On Error`/
    `PROC_ERR` occurrence in the file and reading the Sub directly --
    genuinely missing, not an oversight in reading.

  **Why this is worse in VBA than the JS gap it was found alongside:**
  an unhandled runtime error inside `Document_BeforeSave` -- a real
  Word Application event, not an async fire-and-forget call like the
  JS side -- can surface as a disruptive runtime-error dialog in the
  MIDDLE of an actual Save operation, not just a silently-logged async
  failure. This is inconsistent with this codebase's own established
  convention (`On Error GoTo PROC_ERR` + `Debug.Print`, confirmed
  present in effectively every other routine checked this session:
  `CheckForConflictingRibbonAddIn`, `CountActiveHyperlinks`,
  `AuditBookHyperlinkStyling`, etc.) -- this was a real omission on the
  same-session VBA additions, not a pre-existing project-wide gap being
  newly discovered elsewhere.

  **Planned fix (about to be applied, same session):**
  1. `Document_BeforeSave` gets `On Error GoTo PROC_ERR` at the top and
     a `PROC_EXIT`/`PROC_ERR` block at the bottom, `Debug.Print` only
     (no `MsgBox` -- this handler must stay silent, same reasoning as
     `silent:=True`'s own design intent: never interrupt a Save). On
     error, the hyperlink auto-lock is simply skipped for that save;
     the save itself is NOT cancelled (`Cancel` is never touched).
  2. `LockBookHyperlinks` gets a real `On Error GoTo PROC_ERR` at the
     top (re-established via `On Error GoTo PROC_ERR` immediately after
     the existing narrow bracket's `On Error GoTo 0`, matching the
     exact idiom already used elsewhere in this same file --
     `OptimizedListFontsInDocument`'s `On Error GoTo 0` / `On Error GoTo
     PROC_ERR` pair -- confirmed by reading that Sub directly) and a
     `PROC_EXIT`/`PROC_ERR` block at the bottom, `Debug.Print` only
     (matching this project's "errors to Immediate window, not MsgBox"
     convention for touched handlers -- `PROC_ERR` must not itself pop
     a `MsgBox`, since that would reintroduce the exact
     interrupt-a-silent-auto-run risk this whole fix exists to close).

  Both fixes applied, committed, and pushed: `aeBibleClass` commit
  `5bb1597` (`ThisDocument.cls` + `basTEST_aeBibleTools.bas`).

  block before `Option Explicit`, then accumulated every subsequent line

  VBE-managed metadata, never valid inline code; injecting one literally
  is a syntax error, unlike a true `VBComponents.Import` (used for every
  OTHER module), which parses and applies Attribute lines specially
  rather than treating them as code text.

  [IMPORT] src/basImportWordGitFiles.bas -- ImportThisDocumentFile's
  line-filtering loop now skips ANY line starting with "Attribute "
  (case-insensitive), not just ones before the body starts.

## Real findings this session (not just routine porting)

  1. `Range.getOoxml()` throws `RichApi.Error: GeneralException` on a
     COLLAPSED (zero-length) selection -- a blinking cursor isn't
     enough, every OOXML-based debug hook in this file needs an actual
     highlighted range. Discovered mid-Shape-10-live-check.

  2. `Range.getOoxml()` emits a phantom EMPTY `<w:p/>` stub for a
     paragraph a range's end boundary merely TOUCHES without including
     any of its content (e.g. a selection ending exactly at the next
     paragraph's start). `isEmpty`-based checks misclassify that stub
     as bare. Confirmed workaround: extend the range one character
     past the boundary. Applies to every range-scoped OOXML function
     in this port, not just Shape 10 -- worth remembering for any
     future caller scoping to e.g. a chapter boundary.

  3. Case 80's "next paragraph starts with a page/column break"
     exception is structurally unreachable via ordinary Word editing:
     "end of the empty paragraph" and "start of the next paragraph"
     are the same character position, so Ctrl+Enter there always
     attaches the break to the PRECEDING paragraph, never makes it the
     following paragraph's leading content. Same class of dead-code
     finding as Case 6's own already-documented exception. Left
     honestly unexercised rather than forced.

  4. Shape 13's first live-check reading (`12`, not VBA's usual `0`)
     was correctly explained, not a bug: VBA's baseline of 0 only
     holds for the production document's own `TheHeaders`/`TheFooters`
     styles; a scratch document's stock `Header`/`Footer` styles
     legitimately violate every slot (2 sections x 6 types = 12,
     confirmed; re-verified as 6 on a fresh single-section document).

  5. Word's Font dialog "Dark Red" Standard Colors swatch serializes
     as `#C00000` -- a DIFFERENT color from VBA's `wdColorDarkRed`
     constant (`#800000`, per aeBibleClass Test 88), despite sharing a
